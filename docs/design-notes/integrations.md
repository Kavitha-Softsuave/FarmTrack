# Integrations, alerts, admin, ops: doubts and decisions

Scope: `backend/app/integrations/`, `app/alerts/`, `app/admin/`, Docker, Makefile, CI. Tests: `backend/tests/{integrations,alerts,admin}/`.

## Zoho
- **Mock** (`zoho_mock.py`) reads `farmers.csv` and `advisory_rows_flat.csv`; only `row_kind=self_spray` rows are history (advisor rows are the assumed advisor recommendations, not sprays). Dated by `_spray_datetime`; falls back to the typed `dd/mm/YYYY` at **12:00 IST** (a date alone has no time; midday is the neutral guess). `get_history(until)` is inclusive and never returns later rows.
- Rows with a `_product_id` take ingredient, FRAC/IRAC code and category from the product master (authoritative, ignores the typed group). Rows without one (nutrients, Miravis Duo, Meothrin, Trot) are parsed from the typed text and group: `M3 -> M03`, `IRAC ` prefix stripped, spaces removed (`7 + 3 -> 7+3`), strength/formulation tokens removed from names (`Fenpropathrin 30% EC -> Fenpropathrin`). Category for unknown products is a heuristic: typed group starting with `IRAC` -> `insecticide`, any other group -> `fungicide`, none -> null.
- Nutrient flag: zinc, boron, borax, urea, calcium, magnesium, potassium nitrate, potash, NPK, micronutrient, and the `12.61.00` / `19.19.19` / `13.00.45` grades (separators `.`, `-`, `/`, space). Nutrient rows get no group and no category. The demo's own `_nutrient` helper column is also honoured.
- **Mock writes** (`write_spray`, `write_diagnosis`) append JSONL under `storage_dir/zoho_mock/` and return True (False for a farmer not in `farmers.csv`). **They are not echoed by `get_history`**: the app's own sprays live in the app database and callers merge both sources with `app.integrations.history.merge_history` (dedupes an entry that exists in both: same minute, same product). Platform already uses it.
- **Real adapter** (`zoho_real.py`) is an **untested skeleton**; never run against a real org. India data centre: `accounts.zoho.in` refresh-token flow, `www.zohoapis.in/crm/v6`. Env: `ZOHO_CLIENT_ID`, `ZOHO_CLIENT_SECRET`, `ZOHO_REFRESH_TOKEN`, optional `ZOHO_ACCOUNTS_URL`, `ZOHO_API_BASE`. Missing credentials raise `NotConfigured` at start-up (fail fast). **Assumed, to confirm with the client's org:** module `Contacts`; custom field `Farmer_ID` holds the app's farmer id (`F001`); the sprays are the `Advisory` subform with the field API names of `mock_zoho/contacts.json` (`Self_Spray_Dt`, `Self_Sprayed`, `Self_Spray_Frac_Group`, `Self_Spray_Trade_Name`, `Total_Rainfall_Since_Last_Spray`); contact fields `First_Name, Last_Name, Mobile, Mailing_City, District, Primary_Crop`; a PUT with only a new subform row appends it (existing rows kept); the v6 Notes shape `Parent_Id: {module: {api_name}, id}`. Farmer ids are validated (`[A-Za-z0-9_-]`) before going into a search criteria string. Request shapes are pinned by tests with `httpx.MockTransport`, nothing more.

## IoT and weather
- `MockIoTAdapter`: `latest` = last reading at or before `now`. `is_stale` is the plain age rule (default 48 h). **ST08's scripted outage (10 Jul 06:00 to 14 Jul 18:00) therefore reads as stale from 12 Jul 06:00 to the end of the outage**, not from 10 Jul: on 10-11 Jul the last reading is under 48 h old. The brief said "stale on the scripted offline dates"; the demo scenario S11 (12 Jul 09:00) matches. Random outages shorter than 48 h (up to 35 h in the file) are not stale. Loading the 69k rows takes about 1 s on first use.
- `CsvWeatherAdapter` conventions (shared with Open-Meteo in `weather_common.py`), chosen so the numbers equal the facts in `demo_scenarios.json` (a test recomputes S1, S2, S6, S8 and S3 from the raw CSV): `now` floored to the hour; `hourly_past` = rows `<= now`, last 14 days, oldest first (includes the current hour, needed for S4 where the threshold is reached in the row stamped `now`); `hourly_future` = rows `> now`, 48 h; `rain_last_24h` = `[now-24h, now)`; `rain_next_12h/48h` = `[now, now+N)` (so the current row is counted in the next-N sums and also sits in `hourly_past`: a one-row overlap, kept to match the scenario facts); `daily_forecast` = today plus six days (partial days at the end of the data kept). `stale=True` when the newest row is more than 6 h older than `now` (the archive ends 17 Oct 2026). Before the archive starts, or an unknown station without coordinates, raises `WeatherUnavailable`. Nearest station by coordinates when `station_id` is None or unknown.
- **Open-Meteo licence:** the free `api.open-meteo.com` endpoint is **non-commercial**. Production needs a paid plan: set `OPEN_METEO_API_KEY` and the adapter switches to `customer-api.open-meteo.com` (untested against the real service). `build_weather` logs a warning when `ENV=prod` with `WEATHER_PROVIDER=openmeteo`. The adapter only makes sense with a real clock: the API serves about 14 days back and 7 ahead of the real today. 30-minute cache per place; failures are not cached.
- IMD data is also non-commercial (see `CLAUDE.md`).

## Push
- `LogPushProvider` is the default: logs `device=***<last 4 chars>`, the title and the body length only (no body text, no full token). Note: the platform's log filter redacts anything written `token=...`, so the field is named `device`.
- `FcmPushProvider` (HTTP v1, service-account JWT) is an **untested skeleton**. It needs the `cryptography` package for RS256, which **is not installed in the venv and not in `pyproject.toml`** (see Contract requests). Without it, or without `FCM_CREDENTIALS_FILE`, construction raises `NotConfigured`. Refused pushes (for example an unregistered token) return False and are logged; the evaluator keeps the alert unpushed.
- **SMS (OTP)** is not part of integrations (platform's `security/sms.py` has a log sender only). A real provider (MSG91, Twilio, or the client's gateway) is still a TODO before any real farmer can log in.

## Alerts
- `run_once(session, container, now=None)` commits per farmer (so one failing farmer, station or push cannot lose the others) and returns only the new alerts. Weather is fetched once per station per run. History = Zoho + app diary through `merge_history`; a Zoho outage falls back to the diary and is logged.
- Kinds: `scab_infection_risk`, `marssonina_alternaria_risk`, `late_blight_risk`, `rain_washoff` (yellow and red only; green and other ids ignored) and `waiting_period`. Dedupe keys: `scab:<station>:<date>`, `marssonina:`, `late_blight:`, `washoff:`, `waiting:<product>:<spray date>`; red gets a `:red` suffix, so an escalation alerts once more and a yellow after a red does not.
- **Episode date** comes from `RiskItem.detail` (`episode`, `episode_start`, `period_start`, `spray_at`): the rules engine already sets `period_start` (scab) and `spray_at` (rain wash-off). Leaf spot and late blight carry no start date, so an episode lasts until 5 quiet days have passed since the farmer's last alert of that kind (`EPISODE_GAP_DAYS`): a reminder every ~5 days while the risk persists, not hourly or daily.
- **Stale sensor:** if `iot.is_stale` (or an error reading it) or the snapshot is stale, the body and the spoken text end with "The field sensor is not reporting, so this alert uses the weather forecast only." (Hindi draft) and `payload.sensor_stale` is true. Verified with the real archive: ST08 on 12 Jul 2026.
- **Waiting period** (apple only, because only apple has harvest dates in `stage_calendar.csv`): for each non-nutrient spray in the last 90 days with a known waiting period, safe date = spray date + waiting period; the alert fires for the latest safe date when it is **after the expected harvest date** (band + cultivar, median of the band if the cultivar is unknown). This reads the brief's "waiting period longer than days to harvest" from the spray date, so an old spray does not raise a false alarm. Yellow, red when harvest is 7 days or less away; nothing after the expected harvest date. Products with a blank waiting period (captan) are skipped: the rules engine owns the "ask an expert" case.
- Spoken text = `title. body` through `app.voice.spoken.spoken_out(container.audio, en, hi)`; any failure falls back to text only (an alert is never lost to TTS). All Hindi in alerts is a draft for native review. Numbers in the waiting-period Hindi are digits: the voice layer's number-to-words step must handle them.
- Push: to every device of the farmer in the farmer's language, `data = {alert_id, kind, level}`; `pushed_at` is set when at least one device accepted it.
- **Scheduler** (`alerts/scheduler.py`): APScheduler background jobs, none when `ENV=test` or `ALERT_SCHEDULER=0`. Alerts every `ALERT_INTERVAL_MINUTES` (default 60, first run 30 s after start); Zoho retry for diary entries that failed to sync every 15 min (`maintenance.sync_unsynced_sprays`, my addition: without it a Zoho outage loses the write for good); photo retention daily 03:30 IST (`PhotoStore.purge_expired`, requested by the platform's docstring). Jobs read `app.state.container` at run time. **Run one uvicorn worker**, or every worker runs the jobs. `start_scheduler` also restores the demo clock saved by the admin (`AppSettingRow 'demo_clock'`), even when the scheduler itself is disabled.

## Admin
- `admin/router.py` exports one `router`: the JSON API (`/admin/api/v1`, guarded by `require_admin`, in OpenAPI) plus the HTML pages (`/admin`, cookie login, hidden from OpenAPI). `app.main` needed no change.
- Extra API routes: `GET /alerts`, `POST /alerts/run-now`, `GET /audit`, `GET /photos/{scan_id}/{index}` (hidden from OpenAPI). Review list: open tasks oldest first.
- **Resolve with `release_advice`**: calls `app.state.release_advice(session, task, body)` (platform sets it). Hook returns False or raises -> **502 and the task stays open**. No hook set -> the task is resolved and `resolution.release_status = "not_configured"`. `confirmed_disease` must exist in `disease_catalogue.csv` (422 otherwise); `release_advice` needs a confirmed disease or crop.
- **Pages:** login with the admin key -> signed cookie (HttpOnly, SameSite=Strict, path `/admin`, Secure when `ENV=prod`, 8 h); key and signing secret never reach a page; rotating `ADMIN_API_KEY` or `SECRET_KEY` signs everyone out. CSRF token per session (HMAC) on every POST, plus an Origin/Host check; 5 failed logins per 5 minutes per address are blocked (process-local, like the platform's limiters; use Redis for several workers). **No JavaScript at all**: strict CSP (`default-src 'none'; style-src 'self'; img-src 'self'; form-action 'self'`), the stylesheet is served from `/admin/static/admin.css`, output is auto-escaped, query parameters select fixed messages and are never echoed. Phone numbers are not shown. Photos come from `storage_dir` through a path check (no traversal, no symlink escape, image suffixes only).
- Settings come from `app.state.settings` (platform's `create_app`) with `get_settings()` as fallback; the clock from `app.state.container.clock`.
- Admin sessions use real time, the audit log uses real UTC (as the models say); alerts, review tasks and product overrides use the demo clock.

- The build context is `backend/`; shared data comes in as named contexts (`--build-context data=../data --build-context voice=../voice`; compose does it with `additional_contexts`). Image: python 3.13-slim, deps in a venv from `pyproject.toml` (+ `pg` extras), non-root user (uid 10001), data at `/data`, voice at `/voice`, storage volume at `/app/storage`, healthcheck on `/health`, one uvicorn worker. **No ML dependencies in the image** (`ml` extras are not installed): keep `CROP_ID_PROVIDER` and `DISEASE_PROVIDER` on `stub` until a torch image exists.
- `docker-compose.yml`: `api` + `db` (`pgvector/pgvector:pg16`, named volumes `pgdata`, `storage`), `env_file: ../.env` for the api only, the database gets just `POSTGRES_USER/PASSWORD/DB`; password required via `${POSTGRES_PASSWORD:?...}`; database port not published. Run with `docker compose --env-file ../.env up -d --build` (the Makefile does). The pgvector extension and schema come from the platform's migrations; `VECTOR_STORE` stays `memory` until the RAG agent says otherwise.
