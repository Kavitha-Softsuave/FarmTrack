## Rate limiting (security/ratelimit.py)
- In-memory sliding windows, per process: a restart resets them and N workers multiply the limits. **Production with more than one worker/replica should back the same `hit(key)` contract with Redis.** (The image runs one worker on purpose.)
- Defaults: OTP request 3 per 15 min per phone (the real brute-force and SMS-cost guard) and 60 per 15 min per IP; OTP verify 120 per 15 min per IP (plus 5 attempts per code); refresh 120 per 10 min per IP; wrong admin key 10 per 10 min per IP; ask 20 and scan 30 per 10 min per farmer (LLM/vision cost guard). IP limits are generous on purpose: many farmers share one carrier-grade NAT address. Behind a reverse proxy run uvicorn with `--proxy-headers --forwarded-allow-ips=<proxy>` so `request.client` is the real client; `X-Forwarded-For` is never read by the app itself.
- Keys (phones) live only in memory and are never logged.

## Auth decisions
- Time for OTP expiry, refresh expiry and JWT `exp` is REAL time (`security/timeutil.py`, tests monkeypatch it). Using the frozen demo clock would make an OTP valid forever. Domain timestamps (scans, sprays, alerts, review tasks) use the demo clock as the models say.
- JWT HS256 with a key derived by HMAC from `SECRET_KEY` per purpose (jwt / otp-pepper / refresh), so the key is always 32 bytes and a leaked derived value does not give the others. Rotating `SECRET_KEY` signs everyone out (access and refresh tokens) and invalidates pending OTPs.
- OTP: 6 digits, stored only as sha256(pepper:request_id:code); single use via an atomic `UPDATE ... WHERE consumed = 0` (a test fires 8 parallel verifies: exactly one wins); a new request voids the older code of that phone. Error codes: `invalid_otp` (wrong or unknown request, `details.attempts_left`), `otp_expired`, `otp_attempts_exceeded`, `otp_already_used`, `rate_limited` (429 + `Retry-After`).
- Refresh tokens: opaque 48 random bytes, stored as a keyed hash, rotated on every use. **Replaying an already-rotated token revokes every session of that farmer on that device** (theft signal), so the app must serialise its refresh calls (two parallel refreshes would log the farmer out). One live session per `device_id`; at most 10 live sessions per farmer. Expired: `refresh_token_expired`, anything else `invalid_refresh_token` (401). Added `POST /v1/auth/logout` (body `{refresh_token}`, always 204) so the app can revoke; the access token (60 min) simply runs out.
- 401 `not_authenticated` / `invalid_token` / `token_expired`; admin: missing key 401 `admin_key_required`, wrong key 403 `invalid_admin_key`; other farmers' resources are 404 (never 403).
- Production guard (`security/startup.py`, called by `create_app`, so `uvicorn app.main:app` refuses to start): `SECRET_KEY` must not be the default and must be >= 32 characters, `ADMIN_API_KEY` not the default and >= 16 characters, `CORS_ORIGINS` must not contain `*`. In prod `dev_fixed_otp` is ignored, API docs (`/docs`, `/redoc`, `/openapi.json`) are off and HSTS is sent.

## Errors, headers, logging
- Every error body is `ErrorOut {code, message, details}`. Validation errors (422) are `ErrorOut` plus FastAPI's usual `detail` list (without the offending input value), so both the documented `HTTPValidationError` and `ErrorOut` parse. Unhandled exceptions: a clean 500 with `details.request_id`, traceback only in the server log.
- Middleware (outermost first): security headers (nosniff, DENY, no-referrer, no-store, a CSP for the JSON API; the CSP is skipped for `/admin/` pages and `/docs`, whose own code sets what it needs) -> request id (`X-Request-ID`, a valid incoming one is kept) -> access log (method, path, status, ms; never query string or body) -> body size limit -> CORS. Body limits: multipart `(max_photos * max_upload_mb + 1)` MB, every other body 1 MB; also enforced on streamed bodies without Content-Length (FastAPI turns a reader error into a 400, so the middleware swaps the answer for the 413).
- Logs are JSON on stderr through the `app` logger only (the root logger is untouched). A redaction filter masks phone numbers, JWTs, `Bearer ...`, `otp=`/`code:`/`token=` style pairs and any extra field named phone/otp/token/secret/question; the question text of /ask is never logged (only its length). Other agents' log lines go through the same filter (that is why `PushProvider` logs `device=` not `token=`).

## Uploads and photos
- Only real JPEG/PNG (Pillow decode, `formats=("JPEG","PNG")`; the client's content type and file name are ignored), max `MAX_UPLOAD_MB` each, 1 to `MAX_PHOTOS_PER_SCAN`, at most 40 megapixels (bomb guard). Pixels get the EXIF orientation applied, then the image is re-encoded as JPEG q88 with NO metadata (EXIF, GPS, ICC, PNG text chunks gone), long edge capped at 2048 px. Alpha is flattened onto white. The vision models and the stored file only ever see the cleaned JPEG.
- Stored at `storage_dir/photos/<farmer_id>/<scan_id>/<random>.jpg`; every path goes through `security/paths.safe_join` (no `..`, absolute parts, NUL, symlink escapes). `ScanRow.photo_paths` holds the relative paths (the admin photo viewer uses them).
- **Retention:** photos are kept `PHOTO_RETENTION_DAYS` (365) then deleted by `PhotoStore.purge_expired` (the integrations scheduler calls it daily); the scan result stays. After a purge, adding photos to the scan works (the new ones are analysed alone) but "confirm crop" returns 409 `photos_unavailable`. Whether a year is the right period is a privacy decision for the owner; photos can show people or houses in the background.

## Audio URLs
- `/audio/<sha256>.mp3` (synthesised advice) and `/audio-prompts/<lang>/<id>.mp3` (generated fixed prompts, urls come from the voice catalogue; VOICE's `catalogue.py` documents this route) are **public, no login, name validated by regex** (`^[a-f0-9]{64}\.mp3$`, `^[a-z0-9_]{1,80}\.mp3$` + `safe_join`). `/audio` is immutable and cacheable for a year (content-addressed); prompts are revalidated daily (ETag). Why public: the phone's audio player has no way to send a bearer token reliably, the names are content hashes, and spoken texts hold no personal data. **Rule for every spoken text: never put a farmer's name, phone, village or id in it** (the key is sha256 of the text, so someone who guesses a text could fetch its audio).
- Range requests work (Starlette `FileResponse`), `X-Content-Type-Options: nosniff`.

## Scan pipeline decisions (services/scan_service.py)
- Order and statuses exactly as the brief. Nothing is written until vision, rules and composer have answered: a failure of quality/crop/disease/rules is a 503 `analysis_unavailable` with no row and no files, so the farmer can retry. Optional parts degrade with a log line: weather (rules run with `weather=None`), KB notes (no sources), composer (platform fallback text, `validated=false`; products still come from the rules, and for any non-advice status only "do not spray until an expert has seen it"), audio (text only), Zoho history (diary only, plus a yellow `HISTORY_UNAVAILABLE` warning on the card and in the spoken text), Zoho diagnosis write.
- **Products and timing are copied from the rule output only when `status == "advice"`**; for every other status `AdviceOut.products` is `[]` and `timing` null whatever the rules or composer returned (tested with a deliberately faulty rules fake).
- Crop gate: unknown -> `needs_expert` + ReviewTask (`crop_unknown`), `confirm_crop` shows NO disease or medicine. Spoken text for `confirm_crop` is `crop_is_<crop>` then `crop_confirm_prompt` ("This looks like apple. Is this the right crop?"); the brief listed the two ids the other way round, but that order reads wrong aloud. A crop without a reviewed `crop_is_*` prompt gets a generated sentence from the catalogue name.
- Confirming (`POST /crop`) accepts any crop with data, one the farmer grows, or one the models suggested for that scan (aliases like Corn -> Maize via `app.vision.labels.canonical_crop`); others are 422 `unknown_crop`. A confirmed crop is kept when photos are added. A repeated identical confirmation returns the stored answer without re-running.
- **ScanOut.spoken for rule outcomes is the composer's complete text** (it already says "an expert will look" / "no approved advice" / "no disease seen"); the fixed prompts (`result_expert` ...) are the `next_steps` prompt ids. Only the outcomes that never reach the composer (unusable photo, unknown crop, confirm crop) speak fixed prompts.
- `next_steps`: ok -> mark_sprayed (only if there are products), done; needs_expert -> ask_expert, add_photo (add_photo first when the rules said `needs_more_info`); no_approved_data -> ask_expert; not_a_disease -> add_photo, ask_expert; confirm_crop -> confirm_crop; unusable -> retake (tip). `add_photo` disappears at the photo limit.
- ReviewTask lifecycle: at most one open task per scan; reason `expert_review: low_confidence,...` or `crop_unknown`; closed automatically (`resolution {"auto": "superseded_by_new_result"}`) when a later evaluation no longer needs an expert, EXCEPT a task the farmer asked for (`reason` starts with `farmer_request`). Disease candidates and crop candidates for the admin queue are in `ScanRow.result` (`disease.candidates`, `crop.candidates`).
- Ids of scans, advice, spray logs and tasks created here are time-sortable 32-hex strings (the demo clock is frozen, so `created_at` ties are normal); lists and cursors use the id. `GET /v1/scans` pages with `cursor = last id`.
- `taken_at` (offline queue) is validated and kept in the audit log only: using a phone's real date as "now" would break the demo clock. `lat`/`lon` must come together and be valid; they go to the weather adapter.
- Rate limits count scan, add-photos and confirm calls together (30 per 10 min per farmer).
- The DB session stays open while vision/LLM run (fine for SQLite and MVP volumes; with Postgres release the transaction before the composer call if the pool gets tight).
- No idempotency key on `POST /v1/scans`: an offline-queue retry after a lost response creates a second scan (and a second LLM call). Fix needs a `client_request_id` column (contract request below).

## Other routes
- Spray diary: crop name canonicalised; `advice_id` must be the farmer's own (404 otherwise); a single-product advice needs no `product_id`; product name from the advice, else the product master, else the typed text; at least a product, an advice or free text is required. The record sent to the rules/Zoho is built with integrations' `build_record` (ingredient, FRAC, nutrient flag from the product master/text), history = Zoho + earlier diary entries via integrations' `merge_history`. `check_spray` failing or Zoho failing never loses the farmer's entry (`warnings: []`, `synced_to_zoho: false`; integrations' maintenance job retries). `sprayed_at`: default = demo clock, at most 400 days back, "not in the future" is only enforced when the clock is real (with the frozen demo clock any phone date is "future").
- `/v1/field`: each data source can fail on its own. Stale = sensor stale, weather stale or no weather; no reading falls back to the weather snapshot; spoken summary is qualitative (cold/cool/pleasant/warm/hot, no/light/heavy rain in two days, up to two non-green risks) because the voice rule is "no digits".
- `/v1/ask`: passes the question's `crop_id`, else the farmer's primary crop (RAG note); refusals pass through untouched; 503 `ask_unavailable` if the service raises. Answer audio only for the answer's language.
- `/v1/expert-requests`: always stores a row; with `scan_id` it also opens (or reuses) the scan's ReviewTask. **A request without a scan has no ReviewTask** because `ReviewTaskRow.scan_id` is non-null (contract request below), so the admin queue cannot see it yet.
- `/health`: 200 `{status: ok, db: true}`; if the database ping fails, 503 `{status: "degraded", db: false}` (so a load balancer stops routing). `/v1/meta.providers` lists provider names only.
- `app.state.release_advice` (set at startup) is the hook the admin "send the advice to the farmer" button calls: it re-runs the rules with the agronomist's crop/disease (a confirmed disease counts as confidence 1.0; a confirmed crop alone keeps the model's score); only if the rules then say `advice` is the stored scan result replaced (new AdviceRow, history kept), an in-app alert `expert_advice` created and a push sent. Otherwise it returns False and the admin gets 502 with the task still open. A product an admin disabled is read from `ProductOverrideRow` on every recommendation and **fails closed** (if the table cannot be read, the rules fail and the scan is a 503).
- `GET /audio-prompts/{lang}/{name}` and `POST /v1/auth/logout` are additive routes.

## Database
- Dev/tests: `init_db()` (create_all) and demo-farmer seeding at start-up (`env != prod` or `SEED_DEMO=1`; only into an empty table; crops = primary + other crops, coordinates from `weather/stations.csv`, `created_at` from the clock). Prod: Alembic only (`0001_initial_schema`, generated from the models; a test proves `upgrade head` equals the ORM metadata, downgrade empties it). `alembic.ini` has no URL; `migrations/env.py` uses `settings.database_url` unless a caller sets `sqlalchemy.url`. Do not mix `create_all` and Alembic on the same database (stamp it instead).
- OTP rows of a day ago are deleted on the next OTP request; expired refresh tokens are not purged yet (small table; add to the maintenance job if it grows).

## Contract requests (for the architect)
1. `ReviewTaskRow.scan_id` nullable (or an expert-request link) so scan-less expert requests reach the admin queue.
2. `ScanRow.client_request_id` (unique per farmer) for idempotent uploads from the offline queue.
3. `AlertOut` has no payload or scan id, so an `expert_advice` alert cannot deep-link to its scan (the push `data` carries `scan_id`); an optional `payload: dict` would fix it.
4. `Settings.rules_auto_advice_diseases` (from the RULES notes) and the `cryptography` extra for FCM (from the INTEGRATIONS notes) are theirs, repeated here so they are not lost.
5. `contracts/openapi.json` re-exported by me: additive differences only (see the report): `POST /v1/auth/logout`, `GET /audio-prompts/{lang}/{name}`, integrations' extra admin routes, extra documented error responses (401/404/429/503 `ErrorOut`).
